# Аудит структуры и план перехода на TypeScript — 2026-09-29

Состояние: `dev` после 1.2.0 (i18n, колесо и перетаскивание в режиме меток, быстрое слежение).
Эталон: команда Spok, `spok-ai-setup/plugins/spok` — правила `structure`, `imports`, `code-style`,
`styles` и скилы `app-structure`, `imports-exports`, `code-comments`; для конфигов — `cc-web-new`
(`tsconfig.app.json`, `eslint.config.js`).

Ниже только аудит и план. Код не менялся: скил `app-structure` требует «report, then stop», и
переносы делаются отдельной задачей.

## Итог

1. Переходить на TypeScript стоит. Главная выгода — типы на стыках, где сейчас чаще всего
   ломается: 43 IPC-канала строками в трёх местах, объекты `{width, height, data}`, `fix`, `ring`,
   `status`, ключи переводов. Горячие циклы разбора кадра от TS не замедлятся: типы стираются при
   сборке, код остаётся тем же JS.
2. Структуру менять стоит ещё больше, чем язык. Сейчас приложение держится на 69 глобальных
   функциях и константах, которые страницы подключают `<script>`-тегами в нужном порядке. Есть
   три «god files»: `layer.js` (498 строк, 45 изменяемых переменных модуля), `maps.js` (393),
   `main.cjs` (179). Сначала модули и сборка, потом разбиение по фичам.
3. Фреймворк: React для окна оверлея — можно, по скорости это ничего не стоит (разбор ниже).
   Для слоя на карте игры — нет, там нечего рендерить. MUI — нет, в нашем окне без фокуса это риск.

## Эталон команды: что применимо

| Правило / скил | Применимо | Как |
|---|---|---|
| `app-structure` (фичи = домены, `index.ts` — единственный вход, локальность, без импортов между фичами) | да | `src/features/<domain>`. Для Electron нужно расширить белый список папок: `main/`, `preload/`, `core/`. Скил требует делать это решением команды, а не придумывать в каждой фиче |
| `imports-exports` (группы импортов, алиас `@/*`, без `../../`, только именованные экспорты, двухуровневые barrels, `import type`) | да | с переходом на ES-модули |
| `code-style` (булевы с `is`, 100 символов в строке, без `;`, одинарные кавычки, многострочные объекты, форматирование через ESLint `@stylistic`, **не Prettier**) | да | одним механическим коммитом после TS |
| `code-comments` (комментарий только про «почему») | да, частично | 365 строк комментариев. Много ценных «почему» (факты о фокусе Windows, форматы кадров, пороги) — их оставить; пересказы имён — убрать |
| `styles` / `styles-web` (цвета из токенов, MUI-лестница) | частично | токены уже есть (`:root` в `style.css`, `layer.css`); MUI-часть не применима |
| `stores` / `create-store` (Zustand в `spok-react-sdk`) | нет | не наш SDK. Если окно уйдёт на React, лёгкий store (zustand) в самом приложении уместен |
| `reactuse`, `tanstack-*`, `vercel-react-*`, `styles-native` | нет | только при переходе окна на React; `vercel-react-best-practices/js-*` применимы уже сейчас |

Расхождение в самом эталоне: `code-style` запрещает Prettier, а `cc-web-new` форматирует Prettier.
Для этого репозитория предлагаю следовать правилу: ESLint + `@stylistic`.

## Текущее состояние

- Код приложения: ~3 400 строк (`desktop/` ~700 CJS, `dist/` ~2 100 JS и ~600 HTML/CSS, без сгенерированных данных). Тесты: ~1 400 строк.
- Сборки нет: `dist/` — это исходники, которые Electron грузит как есть. Имя вводит в заблуждение.
- Проверок нет: ни типов, ни линтера, ни форматтера. Зависимости только `electron` и `electron-builder`.
- Стиль: 1 070 строк длиннее 100 символов, 172 длиннее 200; самая длинная — 1 582 (весь API `desktop/preload.cjs` в одной строке), в JS страниц — 654 (`maps.js`). Плотные однострочники, `;`.
- Связи через глобалы:
  - `maps.js` берёт из `app.js` `T`, `parseCoordinate`, `calculateShot`;
  - `layer.js` зависит от 5 скриптов, подключённых раньше него.

  Порядок `<script>` — неявный контракт. Для тестов в Node стоит обходной путь
  `if(typeof module!=='undefined')module.exports=…` в 6 файлах.
- IPC: 43 канала строками, продублированы в `main.cjs`/`map-layer.cjs`, двух preload и страницах. Проверка данных ручная (`cleanStatus`, `cleanClick`, `cleanMemory`) и не связана с отправителем.
- Тесты:
  - 40 юнит-тестов на `node:test`;
  - 8 самописных e2e-проверок на Electron;
  - 4 проверки на Playwright здесь не запускаются: Playwright не установлен;
  - CI гоняет только юнит-тесты.

│  │  ├─ picker/               # выбор области
│  │  ├─ worker/               # terrain-worker

Решения, которые нужно принять командой:
- расширить белый список папок фичи на `core/` и `main/`;
- `src/main` и `src/preload` оставить на верхнем уровне, так как это процессы, а не фичи;
- импорты между фичами, как по канону, только через `@/features/<x>` barrel. `targets` ↔ `game-map`
  сейчас связаны через `scene` и клики — это общий контракт, его место в `shared/ipc`.

## Переход на TypeScript: по шагам, каждый шаг выпускается отдельно

### Шаг 0 — проверки без переноса файлов (≈0,5–1 день)
- `typescript` + `checkJs` + типы в JSDoc на существующих файлах: ошибки типов видны сразу, файлы не двигаются.
- ESLint flat config: `typescript-eslint` + `@stylistic` (блок из скила) + `import/order`, пока с `warn`.
- CI: `tsc --noEmit`, `eslint`, юнит-тесты.

### Шаг 1 — модули и сборка, язык прежний (≈1–2 дня)
- ES-модули вместо глобалов; сборка **esbuild**: одна быстрая зависимость, без dev-сервера.
  Точки входа:
  - `main`, `boot`, `update-core` → CJS;
  - два preload → по одному файлу каждый;
  - три страницы и воркер → IIFE/ESM.
- `target: chrome140/node24`: современный код не переписывается в старый, скорость горячих циклов та же.
- Результат раскладывается **в точности как сейчас**: `desktop/main.cjs`, `desktop/boot.cjs`, `dist/index.html`,
  `dist/layer.html`, `dist/terrain-worker.js`… (ограничение 1). Проверка: `update-check` плюс обновление с 1.2.0 на новую сборку.

### Шаг 2 — TypeScript по файлам (≈3–5 дней)
- Порядок: чистая логика → контракты → main → страницы.
  1. `game-map/core`, `calculator/core`, `shared/geometry`, `shared/i18n`.
  2. `shared/ipc/contract.ts` и preload.
  3. `main`.
  4. Страницы.
- `tsconfig`, как в `cc-web-new`: `strict`, `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`,
  `verbatimModuleSyntax`, `noUncheckedSideEffectImports`, алиас `@/*` → `src/*`.
- `erasableSyntaxOnly` даёт бонус: Node 24 (он внутри Electron 44) запускает `.ts` без сборки,
  поэтому юнит-тесты на `node:test` работают прямо на исходниках.

### Шаг 3 — разбиение по фичам (≈3–5 дней)
- Находки 4–7, 17: `layer.js` на модули с явным состоянием, машина состояний — в чистые функции с юнит-тестами.
- Барьеры: `index.ts` у каждой фичи, без импортов между фичами.

### Шаг 4 — канон стиля (≈0,5 дня)
- `eslint --fix` с `@stylistic` одним коммитом без изменений логики.
- Имена булевых с `is`, чистка комментариев по `code-comments`.

Итого ≈ 2 недели сосредоточенной работы. Каждый шаг проверяется тем же набором: юнит-тесты,
`sweep-check`, `layer-check`, `update-check`, плюс прогон в игре.

### Ограничения, которые нельзя нарушить
1. **Автообновление установленных копий.** Версии 1.x при обновлении проверяют в скачанном архиве
   `desktop/main.cjs` и `dist/index.html`, а запускают `updates/<версия>/desktop/main.cjs` своим
   старым `boot.cjs`. Раскладка результата сборки должна сохранить эти пути, иначе все, у кого
   стоит 1.2.0, не обновятся.
2. **Sandbox preload** не может `require` свои файлы, только `electron`: каждый preload собирается в один файл.
3. **Воркер** грузит `terrain-match.js` через `importScripts`: при сборке он получает свою точку входа.
4. **CSP** `script-src 'self'`: без `eval`, без встроенных скриптов, как сейчас.
5. **Node на этой машине не в PATH**: для сборки локально нужны Node LTS и pnpm (README их уже требует);
   CI (windows-latest) собирает и так.

## Фреймворк: будет ли медленнее

Замедление появилось бы только там, где рендер частый. Где у нас что:

| Часть | Что делает | Фреймворк | Почему |
|---|---|---|---|
| Слой на карте игры (`layer`) | 60–120 кадров/с разбора пикселей, рисует ~10 SVG-меток | **нет** | 95 % времени — числа в `Uint8Array`, фреймворк их не ускорит; рендер меток — 1 `replaceChildren` при движении, React добавил бы только сверку дерева на каждом кадре движения |
| Воркеры поиска | FFT, корреляция | **нет** | рендера нет вовсе |
| Окно оверлея: калькулятор, список целей, меню, статус | обновления по клику и по статусу, несколько раз в секунду | **React — можно** | десятки DOM-узлов, рендер < 1 мс; React + ReactDOM ≈ 45 КБ gzip с локального диска, старт окна +20–50 мс; даёт компоненты вместо 400 строк ручного `createElement`, совпадает с каноном команды (скилы `create-component`, `reactuse`, `vercel-react-*`) |
| Офлайн-карта в окне (SVG, зум, перетаскивание) | `pointermove` до 120 раз/с | React, но императивно | `viewBox` и сетку двигать через `ref`, а не через состояние: перерисовка дерева на каждое движение мыши — единственное место, где React реально замедлил бы |
| MUI | — | **нет** | окно работает без фокуса. MUI Select/Menu/Popover держат фокус через ловушку и порталы — ровно то, из-за чего мы уже заменили системный `<select>` своим списком. Плюс emotion-стили в рантайме и перенос всего HUD-дизайна ради библиотеки, которая здесь мешает |

Рекомендация: сначала шаги 0–3 (TS и структура) — это нужно при любом решении про фреймворк.
React для окна оверлея — отдельным шагом 5, если UI будет расти (настройки, новые панели). Сейчас
окно маленькое, и выгода — в удобстве сопровождения и единообразии с командой, а не в скорости.
Слой и воркеры остаются на чистом TS.

## Что решить

1. Утвердить целевую структуру и расширение белого списка (`core/`, `main/`, `src/main`, `src/preload`).
2. Порядок: шаги 0 → 1 → 2 → 3 → 4, после каждого — выпуск. Или 0–2 одним выпуском.
3. React для окна: сейчас (шаг 5 сразу после 3) или по мере роста UI.
4. Кто ставит Node LTS и pnpm на рабочую машину для локальной сборки.
